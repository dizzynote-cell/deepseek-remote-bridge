# 飞书接入：为什么本阶段没有做

本阶段的任务范围是「本机网页 + 真实 Harness 会话」。飞书属于可选通道，且有一个明确的前置条件，所以没有实现，也没有假装实现。

## 阻塞点

现有 Codex 桥已经在用一个飞书自建应用维持**长连接**接收事件。飞书的长连接按应用维度消费事件：如果 DSH 桥用同一个应用再开一条长连接，同一条消息会被两条连接分别领取，出现重复执行。

因此 DSH 侧要做飞书，必须满足其一：

1. 用**另一个**飞书自建应用（新的 App ID / App Secret / 机器人），事件与消息完全隔离；或
2. 等第二阶段由入口页统一接入，只保留一条长连接，再按已保存的绑定把消息路由给对应后端。

这两条都不在本阶段的授权范围内（没有新的应用凭据，也没有入口页的部署授权）。

## 如果提供独立应用，需要的最小改动

| 组件 | 说明 |
|---|---|
| 配置 | `config/.env` 增加 `DSH_BRIDGE_FEISHU=1`、`FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_VERIFICATION_TOKEN`、`FEISHU_OWNER_OPEN_ID`；密钥只留在本机 |
| 事件接入 | 用 `lark-oapi` 的 WebSocket 长连接（或 HTTP 回调）接收 `im.message.receive_v1`，只处理所有者消息 |
| 路由 | 每条消息带 `chat_id`，映射到该聊天上次使用的 `session-<id>`；未绑定则新建会话并绑定 |
| 发送 | 复用现有 `TaskRunner`：`session/prompt` 提交、`session/wait` 收终态，再把最终回答发回飞书 |
| 卡片 | 批准/提问用飞书互动卡片承接 `/api/interactions` 的同一份请求（`approve`/`reject`/`answer`） |
| 附件 | 飞书图片走 image block，文档下载到 `state/data/uploads/` 后给出路径 |
| 隔离 | 独立缓存、独立同步令牌、独立日志；不与 Codex 桥共享队列或会话映射 |

## 现在能确定的事实

- 本机网页链路已验证可用（列表、历史、发送、工具、批准、提问、附件、余额、语音），飞书只是一个新的入口层，不需要改动执行层。
- 桥的所有写入都经过 Harness 自己的接口，所以飞书通道不会绕过会话锁与批准策略。
- 没有飞书凭据时，`/api/bridge-info` 的 `capabilities` 不会声称支持飞书；页面也不会出现相关入口。

## 结论

飞书缺席是**缺一个独立应用与路由决定**，不是执行层缺口。拿到独立应用后，按上表接入即可，不需要改 Harness 适配器与浏览器端协议。
